# 质量与验收：文件在，不等于观众看懂

制作程序能替你发现缺文件、错哈希、时间冲突和一些已知坏例子。它看不出一句话被观众误读成了什么，也不能替你听完整段口播。这个项目因此把“计划说得通”“真实画面出现了”“画面值得交付”分成不同关口。

## 原有 37 项否决继续有效

杂志插画产线已有的 37 项一票否决，覆盖未经授权发布、PPT 式轮播、假动作、人物跑样、字出框、字幕遮挡、时长不够、音乐压声与素材来源等问题。新增风格继续遵守这些共用底线；杂志独有的纸张画法不强加给其他风格。公开规则目录在 `plugins/muzhi-video-studio/assets/critical-rules.json`。

```bash
python "<PLUGIN_ROOT>/scripts/verify_rule_coverage.py"
```

这条命令会核 37 条规则文本及其引用。通过只表示规则没丢，不表示你的片子已经合格。

## 看状态时，别只看 `passed`

| 你看到的状态 | 它说明什么 | 它没有说明什么 |
| --- | --- | --- |
| `plan_only`，`actual_media_ready: false` | 计划结构和现有输入可能已就绪 | 没有可交付的连续预览媒体 |
| `preview_media_bound`，`actual_media_ready: true` | 当前计划、输入、源码与预览媒体有同版绑定 | 观众已读懂、声音已对齐、用户已批准 |
| `delivery_ready: false` | 交付所需关口未齐 | 不能靠单个 `passed: true` 改写它 |

先用原 `motion_plan` 写明每段的原意、候选选弃、所需素材与可见变化。出片前逐段 `resolve`：真实检索结果、props、源图格式与读窗、源码/输入 SHA、主 Composition 中的组件调用都要核。静态调用链只能证明代码可达，不能证明指定帧真的看见它。渲染后再核输出媒体、关键帧与父子回执；新源码不能事后绑到旧 MP4 冒同版。

示例检查命令：

```bash
python "<PLUGIN_ROOT>/scripts/motion_plan.py" validate --project "<PROJECT_ROOT>" --plan "<PROJECT_ROOT>/motion-plan.json" --stage pre-director
python "<PLUGIN_ROOT>/scripts/production_runner.py" check --workflow studio --stage preview --project "<PROJECT_ROOT>" --plan motion-plan.json
```

一个无声教学例在这里返回 `plan_only` 是正常的。真实有声正式片还需要经本人试听确认的最终音轨、制作助手按该音轨校对的SRT、同版整版导演板与后续门。已锁旧片按原版本和有效备份续作；只有项目实际持有可核的外部封存清单，并精确绑定旧原稿、计划、板和媒体时，才可在原范围内继承旧同稿身份。普通旧目录、手写“legacy”标签或重新绑定的v2不能自动豁免当前同版门；公开包不附带任何人的私人封存清单。

## 片前先看得见、听得到

新片同一份HTML按镜号并列原话/时码、本镜可听的最终声音、接近成片的真实关键帧、画面应发生的变化及可修改处；需要PDF时从同版导出。解释运动关系要有足够不同状态的真实帧；接触、自然行为或节奏光看静帧仍不清楚，就看真实短预演，尚无预演时列为待完成。不能用灰卡、提示词、库示例图或漂亮的首帧替本片镜头请用户批准。

用户可以逐镜指出问题，制作端改完后再给他看当前整版及受影响接力；只有这版真实获确认才进批量，不要求每张图片弹窗批准。展示帧与审核帧必须同一批文件/哈希，HTML也要能由当前计划重建；发现错绑或拿另一页冒同版，就停在片前。正式片的原声、稿、字幕或画面一变，受影响的字幕、镜头与批准范围须重核。片前关键帧批准仍不等于最终运动、音乐和声音通过。

## 把最容易误解的地方逐镜看清

- **原文和解释**：官方页面先证明出处。正文若在手机上太小，再用准确排版给完整句子的独立读窗；不要只放大半句、丢掉限定主语或否定。原页和解释连续出现时，旧高亮应先退场，避免两处同时抢读。
- **数字和图表**：值、单位、分母、轴与画出的形状须来自同一来源。离散件数显示整数；总量不同或口径不一的两组数，不能靠同色同轴变成可比事实。
- **条件与行为**：未知证据保持未知。遮住答案、点亮按钮、纸页接触或光效飞入，都不等于判分、录取、真实点击或动作完成。
- **对象与焦点**：同一物迁移时，原槽与落点不能同时算两个实例；相机推进前应撤掉会被裁成半行的旧标题。镜头停下来后，观众才有机会读主要句子。
- **声音与屏幕**：保原始录音，仅克制清理副本；本人先试听确认最终音轨，制作助手再听音核SRT字词与时码。按实际口播时码看连续画面，在手机尺寸核主字、字幕、边距和焦点；有配乐时在贴片样段及完整母版里听它是否遮声或抢阅读。ASR草稿、差异摘要、文件解码或静音作者时间都不能写成本人原声已同步或字幕已准确。

人工审片最好先不看作者给的解释，让另一位读原稿、看实际媒体后说出自己看见的关系，再比对原意。检查首、中、尾还不够时，就补看动作发生的连续区间。审查可以得出“这项尚未证实”，不必为了让表格全绿替一个未看清的动作签字。

## 测试、CI 与真实影片各做一部分

公开仓的 GitHub Actions 会跑 Python 合同与负例、37 规则和旧产线关键门。两个主入口还须在公开包、空白项目和实际安装根读回；具体 CI 配置见 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)。旧有声同稿和旧无声预览的有限兼容只证明已核输入仍可被当前软件接受，不证明任意新稿、真实ASR或新片视觉质量。`ffprobe` 用于媒体规格，`ffmpeg` 可做完整解码检查；即使都返回零错，也不等于正常速度试听、小屏可读、事实准确或获得公开发布许可。

要向外发布时，还要检查真实素材来源、第三方许可、平台 AI 内容标注以及账号发布状态。[安全说明](SECURITY.md)讲的是权限和数据；它和画面质量一样，不能靠一个“通过”字段代签。
